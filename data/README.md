# Plant and scenario data

YAML under this directory is the **authored source of truth** for MSRR plant
numbers and simulation scenarios. OpenModelica does not read these files.
Python emits Modelica `PlantData` packages:

```bash
python3.12 -m helpers.emit_modelica_plant           # write core/generated/*.mo
python3.12 -m helpers.emit_modelica_plant --catalog # also write data/CATALOG.md
python3.12 -m helpers.emit_modelica_plant --check   # local drift check: fail if generated files drifted
```

Do not edit `core/generated/*.mo` by hand. Do not round-trip YAML through a
dumper (comments would be stripped). Lumped simulations load
`core/generated/MSRR_PlantData.mo` before `MSRR.mo`. SegmentedMSR simulations
load kelvin `core/generated/SegmentedMSR_PlantData.mo` before
`SegmentedMSR.mo`. Startup, transients, and frequency runners load scenario
YAML for CLI tables (`--scenario`, optional `--scenario_file`). Structural
array sizes that `-override=` cannot change are emitted by
`python3.12 -m helpers.emit_scenario_wrapper` into the run directory; default
named 1R/9R vehicles in `MSRR.mo` stay in use so lumped results do not move.
Segmented to-power startups use that wrapper path.

## Layout

- `plants/msrr/` — shared kinetics/materials/loops/poisons plus `cores/r1.yaml`, `cores/r1_10seg.yaml`, `cores/r5x5_z10.yaml`, and `cores/r9.yaml` (`--core_model 1r|9r|1r10seg|r5x5_z10`; the 10-segment and 5x5 cores are segmented-package only). Homogeneous poison data are in `shared/poisons.yaml`; tracking is off until a scenario enables it.
- `plants/msrr/harness/` — documentation-only QA-collapse parity literals (`qModDirect [0.07, 0]`, 1 pcm sine). `load_plant` includes this file in the plant fingerprint; the emitter does **not** write it into product `PlantData`. Collapse maps bind `[Core1R.kG, 0]` (digit-identical 7% on the Single graphite node).
- `plants/msrr_1gw/` — the 1 GW scaled analog of the msrr plant (segmented package only). Every file except the authored `scaling.yaml` is generated by `python3.12 -m helpers.scale_plant --plant msrr_1gw`; the plant carries its own scaled scenario decks under `plants/msrr_1gw/scenarios/` and its own `CATALOG.md`. See [Scaled plants](#scaled-plants).
- `scenarios/startup/`, `transients/`, `freq/`, `campaigns/`, `radial_demos/` — what we *do* to a plant.
- `schema/` — `data/schema/*.schema.json`, the reviewable per-level contract. The file trees and excerpts in this README and in `plants/msrr/README.md` are illustrative, not normative. The `outerFuelAnnulus` block of the shipped disabled plant deck now validates through the quantity envelope (`{value, unit, doc, source}`) and the valueless `status: unsupported` placeholder; the enabled path still refuses a valueless placeholder.
- `CATALOG.md` — generated table of every quantity path, unit, and doc string.

The schemas are the reviewable contract; the loaders enforce the same
requirements at load time. For plant decks, `load_plant`
(`helpers.plant_config`) checks the raw deck — identity fields plus every
included file — and then the merged deck through `validate_plant`: quantity
envelopes and supported units, finite and physical values, coupled array
lengths, the 10-segment core shape (`n_chan = 1`, `n_seg = 10`, per-segment
array lengths of 10, 2-node feedback weights), the 5x5 core shape
(`n_chan = 25`, `n_seg = 10`, per-channel array lengths of 25, 2-node
feedback weights, non-negative `xy` channel centers, and the neighbor-table
pins), and the 9R zone bounds. The 10-segment core also carries physical
sum invariants: `cell_vol` must total the r1 core salt volume (0.4 m³ on
the msrr deck), `q_fiss` 0.93, `q_mod` 0.07 (which must also equal the
deck's `kG`), `kHT` 1.0, and the single-channel `flow_frac` 1.0; grouping
segments 1–5 / 6–10 must additionally reproduce the r1 2-segment values
for `cell_vol`, `q_fiss`, `q_mod`, and `kHT` (the 5+5 coarsening anchor).
The 5x5 core's `cell_vol` and `hAnom` sums are tied to the r1 totals the
same way. Each comparison holds within 1e-9 (relative to the total when it
exceeds 1, so a scaled plant's 100 m³ volume meets the same bar), and a
violation fails with a named error whose field path has the form
`cores.r1_10seg.<array>.value`.
`python3.12 -m helpers.emit_modelica_plant
--check` reaches the same validation through `load_plant`. Scenario decks are
validated by `helpers.scenario_config` on the raw file and again on the fully
merged deck (the runners' `--scenario` and `--scenario_file` paths both go
through it): `extends:` inheritance is checked for cycles and depth, with the
offending chain named on failure, and the requested runner kind must match
the deck's declared `kind`. The shared validation primitives live in
`helpers.data_validation`; a rejected deck fails with a message of the form
`<file>: <field>: <problem>`, naming the repository-relative file and the
dotted field path. The same tree also travels inside the distribution
wheel as the importable `msrr_data` package, which runtime loading
resolves through `importlib.resources` (`helpers.data_resources`) rather
than a repository-relative path.

See `plants/msrr/README.md` for what each plant YAML level holds.

## Plant deck shape

The tracked files of the `msrr` plant deck (reconstructed from `git ls-files
data/plants`):

```text
data/plants/msrr/
├── README.md
├── plant.yaml
├── cores/
│   ├── r1.yaml
│   ├── r1_10seg.yaml
│   ├── r5x5_z10.yaml
│   └── r9.yaml
├── harness/
│   └── collapse_parity.yaml
└── shared/
    ├── core_vessel.yaml
    ├── core_vessel_decisions.md
    ├── decay_heat.yaml
    ├── kinetics.yaml
    ├── materials.yaml
    ├── primary_loop.yaml
    ├── pumps.yaml
    ├── poisons.yaml
    └── secondary_loop.yaml
```

`plant.yaml` defines the plant identity (`schema_version: 1`, `kind: plant`,
`id: msrr`, `display_name`), the two top-level quantities (`nominal_power`,
`total_fuel_vol`), and an `includes:` map that composes the deck
(lines 22–36 of `plant.yaml`):

```yaml
includes:
  kinetics: shared/kinetics.yaml
  decay_heat: shared/decay_heat.yaml
  materials: shared/materials.yaml
  primary_loop: shared/primary_loop.yaml
  secondary_loop: shared/secondary_loop.yaml
  pumps: shared/pumps.yaml
  poisons: shared/poisons.yaml
  outer_fuel_annulus: shared/core_vessel.yaml
  cores:
    r1: cores/r1.yaml
    r1_10seg: cores/r1_10seg.yaml
    r5x5_z10: cores/r5x5_z10.yaml
    r9: cores/r9.yaml
```

The `cores:` map nests `r1: cores/r1.yaml`, `r1_10seg: cores/r1_10seg.yaml`,
`r5x5_z10: cores/r5x5_z10.yaml`, and `r9: cores/r9.yaml`, and the block ends
with `harness: harness/collapse_parity.yaml`.
The harness entry is a documentation-only include that `load_plant` incorporates
into the plant fingerprint, though the emitter never writes it into product
`PlantData`. `load_plant` resolves the map into a merged data object whose
keys reside at the included namespace (`kinetics.*`, `materials.fuel.*`,
`poisons.*`, `cores.r1.*`, ...). The loader validates and the emitter consumes this merged
deck rather than individual files. The `poisons` section is homogeneous
Te-135/I-135/Xe-135 and Pm-149/Sm-149 data (independent yields, reduced-order
worth); it has no topology-sized arrays and carries a required `maturity:`
label (a load-time-validated enum; the committed value is
`reduced_order_pending_review` — see `plants/msrr/README.md`). Tracking
remains off on every production vehicle until a scenario `poisons:` block
enables it. The emitter
writes `SegmentedMSR_PlantData.Poisons` only; lumped `MSRR_PlantData` has no
poison record. The CLI flag `--core_model 1r`, `9r`,
`1r10seg`, or `r5x5_z10` selects `cores.r1`, `cores.r9`, `cores.r1_10seg`, or
`cores.r5x5_z10`.

Every physical quantity in a plant deck is a **quantity envelope**: a scalar
or homogeneous numeric `value`, an explicit `unit` (`"1"` for dimensionless),
a `doc` string, and an optional `source` (lines 4–11 of
`shared/kinetics.yaml`):

```yaml
num_groups:
  value: 6
  unit: "1"
  doc: Number of delayed-neutron precursor groups.
  source: MSRR.Components.MSRR1R.numGroups
lambda:
  value: [0.0124, 0.0305, 0.111, 0.301, 1.14, 3.014]
  unit: 1/s
```

Field `doc:` is copied verbatim into `data/CATALOG.md`, while `source:` records
the Modelica path or reference provenance for the parameter values. Two leaf
structures occur in the decks:

- **quantity envelopes** — standard for physical quantities; the loader and
  emitters extract `value` and `unit`;
- **bare policy scalars** — unadorned scalars without a `value`/`unit` wrapper
  where the value defines modeling policy directly:
  `graphite_split_policy: raw_kHT_sum` in `cores/r9.yaml` (the 9R graphite-direct
  power fraction is the `kHT1 + kHT2` sum of the Sigma=1-renormalized deposition
  arrays, total ≈ 0.060730; it is never forced to the 1R 7% share;
  `load_plant` rejects any other value) and `fission_fraction: 0.95`
  under `forcing.uhx_demand` in `data/scenarios/startup/to_100kw.yaml`.

**Unit rule.** Temperatures are stored in `degC` (the lumped native unit) in
the plant YAML. Lumped `MSRR_PlantData.mo` emits them unchanged; the
segmented emitter writes `SegmentedMSR_PlantData.mo` in kelvin, adding
273.15 to every quantity annotated `degC` (trim setpoints, initial
temperatures, and ambient temperatures). Each written
`core/generated/*.mo` begins with an informational
`// Emitter git revision:` comment naming the emitting checkout's
revision (`unknown` outside a Git checkout); `--check` ignores that
line.

**9R core shape.** The 9R core deck defines 9-element per-region arrays
(`vol_F1`, `kFN1`/`kFN2`, `kHT1`/`kHT2`, `IF1`/`IF2`, ..., `TG_regions`)
along with a four-zone flow structure: 1-based region bounding indices
`zone_start` and `zone_end` (Z1 = {R1}, Z2 = {R2–R4}, Z3 = {R5–R7},
Z4 = {R8–R9}) and `n_seg_zone: [2, 6, 6, 4]`, specifying the number of salt
cells in each zone chain.

**10-segment core shape.** The 10-segment core deck (`cores/r1_10seg.yaml`,
CLI key `1r10seg`) defines 10-element per-segment arrays (`cell_vol`,
`q_fiss`, `q_mod`, `kHT`) for a single channel (`n_chan = 1`,
`n_seg = 10`), with `dz = 0.14` m per segment. The feedback weights stay
2-node (`IF = [0.5, 0.5]`, `IG = 1.0`) because the product feedback API is
2-node: segments 1–5 / 6–10 map to fuel nodes 1 / 2. The values are a
uniform first-cut partition of the r1 2-segment totals — no measured axial
profile exists in the repository, and grouping segments 1–5 / 6–10
reproduces the r1 values exactly (see the coarsening anchor in
`plants/msrr/README.md`).

**5x5 core shape.** The 5x5-radial core deck (`cores/r5x5_z10.yaml`, CLI key
`r5x5_z10`) defines per-cell arrays (`cell_vol`, `q_fiss`, `q_mod`, 250
entries each) and per-channel arrays (`flow_frac`, `hAnom`, 25 entries each)
for the 5x5 staggered triangular lattice: `n_chan = 25`, `n_seg = 10`,
`dz = 0.14` m per segment, and an inventory-consistent EFFECTIVE lattice
(physics review 2026-09-27; it replaces the 0.02 m placeholder inherited from
the one-channel decks). Pitch 0.266825 m and `chanR = 0.0603144` m per channel
are chosen so that each model channel's lattice cell holds its graphite and
salt over H = 10*dz. `SegmentedMSR.Core.ChannelMap` computes
`modAnnulusArea = cellCrossSection − π·chanR²` = 0.0502286 m²
= `vol_graphite/(25*H)`, consistent with the moderator heat capacity; it is
not sourced from the deck's `channel_geom.Ac = 0.0`. The neighbor-pair
conductance `G_ck = k_mod*dz/sqrt(3)` stays pitch-independent, and
`xy` channel centers stored translated by +2p in x so every coordinate is
non-negative — the shared data envelope rejects negative meters, and the
translation is physics-inert because the Modelica neighbor matching is
distance-based. The feedback weights stay 2-node (`IF = [0.5, 0.5]`,
`IG = 1.0`): segments 1–5 / 6–10 of all 25 channels map to fuel nodes 1 / 2.
The values are a uniform first-cut partition of the r1 totals — no measured
radial power/flow profile exists in the repository, and the per-channel
column sums equal the `r1_10seg` data exactly (cell_vol 0.04 m³, q_fiss
0.093, q_mod 0.007, kHT 0.1 per segment; flow 1.0; hAnom 4565 W/K on the
PSAR-basis data, 2.4916e4 W/K before). The
deck also carries the first non-zero product `k_mod` (86.0 W/(m.K), first cut
from the INL G-348 measured graphite k(T) correlation evaluated at 570 degC;
MSR-1 graphite-grade confirmation is an open follow-up) and the 5x5
neighbor-table pins (56 undirected edges, 112 directed of 150 slots;
per-degree channel counts {2:2, 3:5, 4:6, 5:3, 6:9}); see the 5x5 anchor in
`plants/msrr/README.md`.

**Outer-annulus fission: configured vs active (TASK-20260922-03 P2).**
The manifest record's `fissionEnabled` is the CONFIGURED (authored)
`fission.enabled` flag: it stays on the record together with both
fraction vectors (`fissionSourceFraction`,
`fissionHeatDepositionFraction`) in every enabled state, including
fission-disabled. The STRUCTURALLY ACTIVE state is decided once by
`helpers.plant_config.outer_annulus_fission_active` — configured AND
`math.fsum(heat_deposition_fraction) > 0` — inside
`helpers.segmented_runs.outer_fuel_annulus_run_contract`, and
`OuterAnnulusRunShape.fission_enabled` carries that ACTIVE image. It is
the same conjunction the Modelica `fissionOn` switch evaluates
(`outerOn and fissionEnabled and sum(heatDepositionFraction) > 0`,
`core/SegmentedMSR.mo:6193` and `:14202`), so a fission-enabled deck
with an all-zero heat-deposition distribution folds to the established
no-fission equations in Modelica and carries no fission columns in
Python: only a fission-active deck appends the six
`OUTER_ANNULUS_FISSION_COMPACT_COLUMNS` (`QFissionActiveCoreW`,
`QFissionOuterAnnulusW`, `QDecayOuterAnnulusW`,
`fissionPowerClosureResidualW`, `VIrrEffM3`, `annulusFeedbackPcm`).
No CLI flag selects the fission state — it comes from the plant deck.
Shipped state stays disabled with zero vectors and
`production_enablement.status: blocked`; the synthetic 5% split lives
only in the `R1_10SegOuterFuelAnnulusFissionCavity` demo
(`datasetId = 'SYNTHETIC-P7-FISSION-DEMO'`,
`maturity = 'synthetic'`).

│   ├── nominal_sweep.yaml

│   └── paper_time_example.yaml
├── radial_demos/
│   ├── radial_1r10seg_circulating_adiabatic.yaml
│   ├── radial_1r10seg_circulating_cooled.yaml
│   └── radial_1r10seg_static.yaml
├── startup/

│   └── to_1mw.yaml

`freq/fr_gain_prior.json` is not a scenario: it is the frequency-response
gain prior (measured `|G(omega, P)|` and resonance parameters of the
`review-2026-09` campaign) that sets the target-swing perturbation amplitude
and the settling discard of legacy sweeps. It is generated by
`python3.12 -m freq.build_gain_prior` (see `freq/README.md`); scenario
discovery reads `*.yaml` only.

Field `kind` selects the subdirectory (`startup/`, `transients/`, `freq/`,
`campaigns/`, `radial_demos/`), and `id` specifies the stable scenario name passed to
`--scenario`. Scenario IDs resolve from the `id:` field rather than the file
name: for example, `data/scenarios/startup/approach_to_criticality.yaml` sets
`id: startup`, so `--scenario startup` executes that file by default.

Section roles, one line per section (sourced from the property descriptions
of `data/schema/scenario.schema.json`):

| Section | Holds |
|---|---|
| `schema_version` | Schema version; must be `1`. |
| `kind` | Scenario family (`startup`, `transients`, `frequency`, `campaign`, `radial_demo`); maps to the `data/scenarios/` subdirectory. |
| `id` | Stable scenario name passed to `--scenario` (resolved by `id:`, not file name). |
| `doc` | Free-text description of the scenario. |
| `applies_to` | Plant core IDs the deck applies to, e.g. `[msrr.r1, msrr.r9, msrr.r1_10seg, msrr.r5x5_z10]`. Every shipped deck that carries an `applies_to` key lists all four production cores; the exceptions are the three `radial_demos/` decks, which list only `msrr.r1_10seg`, and the campaign deck `campaigns/review-2026-09.yaml`, which carries no `applies_to` key (it composes named scenarios via `cores: [r1, r9]`). Runners enforce the list for the decks that carry it, after CLI-to-YAML core conversion: a selected core absent from `applies_to` refuses before wrapper generation or simulation, and the deliberate `--allow-unlisted-core` override is recorded in the run provenance. |
| `package_support` | Legacy vehicle class names per core, and whether the segmented path requires a generated wrapper. |
| `extends` | Optional parent scenario ID or file stem; maps are deep-merged (see below). |
| `numerics` | Experiment-specific integration parameters: `stop_time`, intervals, solver method, and maximum step size. |
| `structural` | Array lengths emitted into wrappers (`numUhxSteps`, `numSourceSteps`, ...); not read directly as OpenModelica array dimensions. |
| `forcing` | Boundary forcing schedules (source, reactivity, UHX demand, pump ramps, sinusoidal perturbation); not plant volumes. |
| `cases` | Named transient cases (step reactivity in pcm, flow fraction, and `uhx_trip` schedule); runners load `STEP_PCM` and `FLOW_CASES` from this list. |
| `grid` | Frequency-sweep angular frequency range and point count; CLI flags `--freq_min` and `--num_freq` override these when supplied. |
| `init` | Setpoint-row selection and per-core temperature overlays; `per_core` keys are `r1`/`r9` only, so the segmented-only cores `r1_10seg`/`r5x5_z10` get no temperature overlay by schema design. Does not hold the raw setpoint CSV table. |
| `display` | Plot phase lines and display windows; not evaluated by OpenModelica. |
| `vehicle` | Committed `SegmentedMSR.Demos.<name>` demo vehicle class the deck runs (`radial_demo` kind). |
| `maturity` | Dataset maturity label (`radial_demo` kind); the loader requires exactly `exploratory_geometry`. |
| `radial_config` | Structural radial/loop identity the deck claims (`radial_demo` kind); unknown keys are refused and the claimed identity must equal the named vehicle's code-owned contract field by field. |

**`extends:` is a deep-merged overlay.** `data/scenarios/startup/to_100kw.yaml`
names its parent by file stem:

```yaml
extends: approach_to_criticality
```

Nested maps merge key by key, while scalars and arrays are replaced
wholesale, so the child keeps its own `id` (`startup_to_100kw`) and the
parent's id is recorded as `_parent_id` on the merged deck. For example,
`startup_to_100kw` inherits the parent named `startup` (the deck
`approach_to_criticality`) and overrides only the modified values:
`numerics.stop_time_s` (151200 s rather than
108000 s), `numerics.number_of_intervals` (151200 rather than 1080000), and
`structural.numUhxSteps` (9 rather than 1). Explicit CLI flags take precedence
over YAML values: runners populate parameters from the deck only when the
matching flag is omitted from the command line. Scenario decks use the same two
leaf kinds as plant decks: quantity envelopes (`init.per_core.r1.TF1`,
`forcing.source.strength`) and bare scalars (`fission_fraction: 0.95`,
`heat_loss: true`). Campaign decks (`kind: campaign`) compose named scenario
files rather than duplicating their tables (`campaigns/review-2026-09.yaml` maps
each workflow to a scenario ID).

## Scaled plants

A scaled plant is a second deck derived from a base deck by explicit
scaling rules, so it stays in step when the base changes. Its authored
input is one file, `plants/<id>/scaling.yaml`: the base plant, nominal
power, core power density relative to the base, and core temperature rise
(`core_temperature_rise_K`), plus three optional keys the 1 GW analog sets
for its freeze margins: `reference_temperature` (630 degC, the isothermal
reference; the base 570 degC by default), `hx_ua_factor` (2, the
intermediate-HX UA beyond the power scaling), and
`results_ii_uhx_demand_follows_flow` (true: the scaled Results II flow
cases get `uhx_demand_follows_flow`).
`helpers.scale_plant` writes the rest of the deck: every base quantity
follows a named rule, and a quantity without one stops generation. The
generated README of `plants/msrr_1gw/` lists the derived design (1 GW at
4x the msrr power density: volumes x250, lengths x6.30, 3453 fuel
channels of the msrr lattice, 100 K core rise) and its known limits.

Three parts of a scaled deck are not plain rescalings:

1. The core salt-graphite hA comes from `helpers.core_ha_scaled` for the
   scaled geometry. The 1 GW channels run transitional at nominal flow, so
   the msrr_1gw core decks carry the two-branch flow law `hA_lam_frac` /
   `hA_lam_exp` beside `hAExp` (absent keys mean the single power law, as
   on every msrr core).
2. The `segmented_steady_state` blocks come from
   `helpers.segmented_trim_levels --plant <id> --write`; the generator
   keeps them once written.
3. The scenario decks under `plants/<id>/scenarios/` scale absolute powers
   and source strengths with the nominal power and restate the Results II
   step amplitudes in the plant's own dollar; ids naming an absolute power
   change (`startup_to_100mw`, `startup_to_1gw`).

The segmented runners select a plant with `--plant <id>`: the plant's
generated `core/generated/<id>/SegmentedMSR_PlantData.mo`, its scenario
tree (no fallback to `scenarios/`), and default outputs under
`00runs/segmented/<id>/`. The legacy lumped package stays msrr-only.
